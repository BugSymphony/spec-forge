# Comic 创作宪法

## 核心创作原则 (Core Creative Principles)

### I. Spec 驱动 (Spec-First, NON-NEGOTIABLE)

**所有创作必须始于完整的 Spec 文档**：

- 世界观设定必须完整且视觉化
- 角色档案必须包含外貌特征、性格、能力
- 剧情架构必须有清晰的分镜规划和节奏控制
- 美术风格必须明确画风、色彩、分格方式
- **禁止**在没有 Spec 的情况下直接开始绘制

### II. Plan 指导 (Plan-Guided)

**每个项目必须有创作策略计划**：

- 从 Spec 中提取核心视觉概念和叙事策略
- 明确漫画类型（少年/少女/青年/儿童）
- 进行合规性检查（Constitution Check）
- 定义清晰的页面结构和交付格式
- **只关注"做什么"和"为什么做"**，不涉及具体分镜

### III. Tasks 分解 (Task-Breakdown)

**Plan 必须拆解为可执行的绘制任务**：

- 每页有明确的分镜数、对话量、视觉重点
- 任务之间有清晰的依赖关系和顺序
- 每页任务包含构图、线稿、上色、文字
- **这是 tasks 命令的职责**，不应在 Plan 阶段涉及

### IV. 一致性维护 (Consistency Maintenance)

**所有产出必须严格遵循 Spec 和 Plan 的约束**：

- 角色形象必须保持一致（发型、服装、比例）
- 美术风格必须统一（线条、色彩、光影）
- 叙事节奏必须符合预设的分镜规划
- 对话框和文字排版必须规范
- **每次生成后必须进行 Schema 校验**

### V. 质量优先 (Quality-First)

**每个阶段的产出必须符合质量标准**：

**Spec 阶段标准**：

- 世界观视觉化且自洽
- 角色设计有辨识度和吸引力
- 剧情有足够张力和画面感
- 约束条件清晰可行

**Plan 阶段标准**：

- 视觉策略明确且可执行
- 分镜规划完整
- 合规性检查通过
- 页面结构清晰

**Tasks 阶段标准**：

- 每页任务目标明确
- 任务之间逻辑连贯
- 可执行性强

**Dist 阶段标准**：

- 页面符合 Spec/Plan/Tasks 的所有约束
- 画面流畅、节奏合理
- 角色表演符合人设
- 无构图或透视错误

## 创作流程规范 (Development Workflow)

### 阶段顺序（严格执行）

```
1. Specify → 2. Plan → 3. Tasks → 4. Implement (页面草稿)
```

**禁止跳过任何阶段**，每个阶段的输出是下一阶段的前提。

### 各阶段职责边界

| 阶段          | 职责        | 输出文件             | 核心问题                |
|-------------|-----------|------------------|---------------------|
| **Specify** | 定义漫画大纲和设定 | `specs/spec.md`  | What & Why          |
| **Plan**    | 制定视觉策略和方向 | `specs/plan.md`  | Strategy & Approach |
| **Tasks**   | 拆解为页面绘制任务 | `specs/tasks.md` | How to Execute      |
| **Dist**    | 产出最终页面草稿  | `dist/pages/` | Final Content       |

### 跨阶段反馈机制

- **Dist → Spec**: 页面绘制中发现设定问题时，需反向更新 Spec
- **Tasks → Plan**: 任务分解发现视觉策略问题时，需反向更新 Plan
- **Plan → Spec**: 策略规划发现大纲缺陷时，需反向更新 Spec
- **所有变更必须记录版本历史**

## 文档组织标准 (Documentation Standards)

SpecForge 采用三层架构模型：

```
specs/   → 规范层（Declarative Layer）
build/   → 中间结构层（Structural Artifact Layer）
dist/    → 最终产物层（Output Layer）
```

### Specs/ 目录结构

```
specs/
├── spec.md              # 原始漫画大纲与设定（输入文件）
├── plan.md              # 视觉策略总纲
└── tasks.md             # 页面绘制任务分解
```

### Build/ 中间结构层

```
build/
├── xxx.md
```

### Dist/ 目录结构

```
dist/
└── pages/
    ├── page_001.md    # 第 1 页：[页面描述]
    ├── page_002.md    # 第 2 页：[页面描述]
    └── ...
```

## Schema 校验要求 (Schema Validation Requirements)

### 强制校验点

1. **Spec 生成后** - 必须通过 `schema.yaml` 校验
2. **Plan 生成后** - 必须通过 `plan-schema.yaml` 校验（如有）
3. **每页完成后** - 必须检查是否符合 Spec/Plan 约束

### 校验维度

- **完整性检查**: 必填字段是否齐全
- **一致性检查**: 是否与已有设定冲突
- **可行性检查**: 规模、复杂度是否在可控范围内
- **质量检查**: 是否符合各阶段的质量标准

## 工具使用规范 (Tool Usage Guidelines)

### Forge 命令使用

| 命令                            | 用途       | 输入               | 输出                           |
|-------------------------------|----------|------------------|------------------------------|
| `forge specify --idea="..."`  | 生成 Spec  | 创意想法             | `specs/spec.md`              |
| `forge plan`                  | 生成 Plan  | `specs/spec.md`  | `specs/plan.md`              |
| `forge tasks`                 | 生成 Tasks | `specs/plan.md`  | `specs/tasks.md`             |
| `forge implement --page=N`    | 生成页面     | `specs/tasks.md` | `dist/pages/page_N.md`       |

### LLM 使用原则

- **AI 辅助，人类审核**: AI 生成草图，人类审核修正
- **迭代优化**: 接受初稿不完美，通过多轮对话改进
- **保持上下文**: 每轮对话提供足够的背景信息（Spec/Plan/Tasks）
- **明确边界**: 清楚说明当前处于哪个阶段，需要何种输出

## 版本控制 (Version Control)

### 文档版本管理

- **Spec**: 重大设定变更时升级版本号（v1.0 → v2.0）
- **Plan**: 策略调整时更新日期和版本
- **Tasks**: 任务调整时保留历史记录
- **Pages**: 每页保留修改历史

### 变更记录格式

```markdown
## Changelog

### v2.0 (2026-03-19)

- 修改：[具体内容]
- 原因：[变更理由]
- 影响：[影响范围]
```

## 治理与修正 (Governance & Amendments)

### 宪法权威

本宪法是该漫画创作项目的最高准则，所有其他实践和约定都必须遵循本宪法。

### 修正流程

1. **提出修正**: 任何参与者都可以提出宪法修正建议
2. **讨论评估**: 团队讨论修正的必要性和影响
3. **记录变更**: 在 Changelog 中记录修正内容和理由
4. **更新版本**: 升级宪法版本号

### 违规处理

- **轻微违规**: 在代码审查或内容审核中指出并修正
- **严重违规**: 暂停相关阶段，重新审视 Spec/Plan 的合理性
- **系统性问题**: 触发宪法修订流程
