## 检查清单目的：「对英文做的单元测试」

**核心概念**：检查清单是对**需求书写质量的单元测试**——验证给定领域中需求的完整性、清晰性和一致性。

**不用于验证/测试**：
- ❌ 不检查 "章节内容是否精彩"
- ❌ 不测试 "情节转折是否正确"
- ❌ 不确认 "输出文件是否存在"
- ❌ 不检查代码/实施是否匹配规格

**用于需求质量验证**：
- ✅ "所有类型卡片的视觉层次需求是否已定义？"（完整性）
- ✅ "'突出展示'是否用具体的尺寸和位置量化？"（清晰性）
- ✅ "所有交互元素的悬停状态需求是否一致？"（一致性）
- ✅ "键盘导航的无障碍需求是否定义？"（覆盖性）
- ✅ "规格是否定义了图片加载失败时的回退行为？"（边缘情况）

**比喻**：若将规格视为用英文编写的代码，检查清单就是它的单元测试套件。测试的是需求是否写得足够好——完整、无歧义、一致，可以进入创作阶段。

## User Input

```text
$ARGUMENTS
```

**必须**在继续之前考虑用户输入（若不为空）。

## Pre-Execution Checks

1. 确认当前目录为 SpecForge 项目：检查 `.specforge/` 目录是否存在
2. 执行 `specforge show --paths-only` 获取当前活动 feature 路径：
   - 提取 `FEATURE_DIR` 和 `SPEC_FILE`
   - 若不存在，ERROR：无法确定 feature，请先执行 `/specforge.specify`
3. 执行 `specforge show --artifact spec` 加载规格内容
4. 执行 `specforge show --paths-only` 获取 `IMPL_PLAN` 和 `TASKS_FILE` 路径（若存在）
5. 读取 `.specforge/templates/checklist-template.md` 作为结构参考
   - 若模板不存在，使用默认 H1 标题 + 元信息 + `##` 分类章节结构

## Outline

### 第 1 步：澄清意图（动态生成）

从用户输入和规格中提取信号，生成最多 3 个初始上下文澄清问题。问题必须：

- 源自用户的措辞和规格/计划中的信号
- 仅询问会实质性改变检查清单内容的信息
- 若 `$ARGUMENTS` 中已明确则跳过

**生成算法**：
1. 提取信号：领域关键词（创作类型、质量维度）、风险指标（"关键"、"必须"）、利益相关者提示（"审查"、"验收"）
2. 将信号聚类为候选关注域（最多 4 个），按相关性排序
3. 识别缺失维度：范围广度、深度/严格性、风险重点、排除边界、可度量验收标准
4. 形成问题：
   - 范围细化（如「是否应包含 X 和 Y 的集成接触点，还是仅限本模块？」）
   - 深度校准（如「是轻量级预提交检查还是正式发布门禁？」）
   - 边界排除（如「是否本阶段明确排除性能调优项？」）

**交互不可用时的默认值**：深度→标准，受众→创作者本人，重点→前 2 个相关性集群

### 第 2 步：加载功能上下文

从 `FEATURE_DIR` 读取：

- **spec.md**：创作需求、范围、成功标准
- **plan.md**（若存在）：创作上下文、结构方案、设计文档
- **tasks.md**（若存在）：任务清单和依赖关系

**上下文加载策略**：
- 仅加载与活跃关注域相关的必要部分（避免全量转储）
- 将长段落总结为简洁的场景/需求要点
- 若源文档过大，生成中期摘要条目而非嵌入原始文本

### 第 3 步：生成检查清单 — 「需求质量的单元测试」

在 `FEATURE_DIR/checklists/` 目录下生成检查清单：

- 若目录不存在：创建
- 生成唯一文件名：使用简短描述性名称（如 `content-quality.md`、`structure.md`、`consistency.md`）
- 文件处理规则：
  - 文件不存在 → 新建，从 CHK001 开始编号
  - 文件已存在 → 追加到现有文件，从最后一个 CHK ID 继续（如最后是 CHK015，从 CHK016 起）
- **禁止删除或替换现有内容**

#### 核心原则 — 测试需求而非实施

每个检查清单项必须评估**需求本身**的质量维度：

- **完整性**：所有必要需求是否都已记录？
- **清晰性**：需求是否明确且无歧义？
- **一致性**：需求之间是否对齐无矛盾？
- **可度量性**：需求是否可以客观验证？
- **覆盖性**：所有场景/边缘情况是否都有对应需求？

#### 分类结构 — 按需求质量维度分组

1. **需求完整性**：所有必要需求是否已记录？
2. **需求清晰性**：需求是否具体且无歧义？
3. **需求一致性**：需求之间是否对齐无冲突？
4. **验收标准质量**：成功标准是否可度量？
5. **场景覆盖性**：所有流程/情况是否都有对应需求？
6. **边缘情况覆盖性**：边界条件是否已定义？
7. **非功能性需求**：性能、质量、可维护性等是否已明确？
8. **依赖与假设**：是否已记录并验证？
9. **歧义与冲突**：哪些需要澄清？

#### 条目书写规则

**❌ 错误**（测试实施）：
- "验证首章有 3 个以上情节转折"
- "检查人物对话风格一致"

**✅ 正确**（测试需求质量）：
- "每章的字数范围是否在内容规模中明确定义？[完整性]"
- "'引人入胜的开场'是否用可度量的特征量化？[清晰性，Spec §创作目标]"
- "各章节的人物行为是否有一致性需求？[一致性]"
- "是否定义了章节间衔接的断点处理需求？[覆盖性，Gap]"

**条目结构**：
- 问题形式询问需求质量
- 关注规格/计划中写了什么（或没写什么）
- 方括号标注质量维度 `[Completeness/Clarity/Consistency/etc.]`
- 有对应规格章节时引用 `[Spec §X.Y]`
- 检查缺失需求时使用 `[Gap]` 标记

**追溯性要求**：
- 最低：≥80% 的条目必须包含至少一个追溯引用
- 每个条目应引用：规格章节 `[Spec §X.Y]`，或使用 `[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]` 标记

**内容合并**：
- 若原始候选条目 > 40，按风险/影响优先级排序
- 合并检查同需求方面的近似重复项
- 若 > 5 个低影响边缘情况，合并为 1 条："X、Y、Z 等边缘情况的需求是否已覆盖？[Coverage]"

### 第 4 步：写入检查清单文件

按照 `.specforge/templates/checklist-template.md` 的结构生成。若模板不可用，使用：
- H1 标题
- 目的/创建/功能元信息行
- `##` 分类章节
- `- [ ] CHK### <需求质量条目>` 行，ID 全局递增

### 第 5 步：报告完成

输出完整路径、条目数、新建还是追加。摘要：
- 选择的关注域
- 深度级别
- 受众/时机
- 用户明确指定的必含项

## Output

- **制品**：`FEATURE_DIR/checklists/[domain].md`
- **格式**：Markdown 检查清单，`- [ ] CHK### <条目>`
- **编号**：全局递增（CHK001、CHK002...），跨文件不重复

## Stage Checkpoints

- [ ] 用户意图已澄清（最多 5 个问题）
- [ ] 规格和计划上下文已加载
- [ ] 检查清单分类涵盖完整性和清晰性维度
- [ ] 条目遵循「测试需求而非实施」原则
- [ ] ≥80% 条目含追溯引用（[Spec §X.Y] / [Gap] / [Ambiguity] 等）
- [ ] CHK 编号全局递增，追加模式下从已有最大 ID 继续

## 质量门禁

- 每个条目是否评估需求质量而非实施行为？
- 是否避免了 "验证"、"测试"、"确认" + 实施行为的模式？
- 是否涵盖了完整性、清晰性、一致性、覆盖性四大维度？
- 追溯引用是否足够（≥80% 有引用）？
- 所有 CLI 调用是否使用了 `--json` 参数（如适用）？
- 本文件中是否**不包含** git、branch、commit、hook 相关引用？

## 检查清单一览表

每个 `/specforge.checklist` 调用使用简短描述性文件名，可新建或追加到已有文件。这允许：

- 多种类型的检查清单（如 `content-quality.md`、`structure.md`、`consistency.md`）
- 简洁易记的文件名（指示清单用途）
- 在 `checklists/` 文件夹中轻松识别和导航

为避免杂乱，使用描述性文件名，完成时清理已过时的检查清单。

### 内容类型特定检查清单示例

**小说内容质量** (`narrative-quality.md`)：
- "每章的情节推进是否与人物弧线对齐且有明确目标？[Completeness]"
- "'紧张感'是否用具体的情节元素和节奏定义量化？[Clarity]"
- "人物对话风格是否在全文有一致性需求？[Consistency]"
- "是否定义了章节结尾的悬念设置需求？[Coverage, Gap]"

**文章逻辑性** (`logic-structure.md`)：
- "每个论点的支撑论据数量是否在规格中定义？[Completeness]"
- "'充分论证'是否用具体的最少论据数或引用数量化？[Clarity]"
- "反面观点的处理策略是否在各个论点间一致？[Consistency]"
- "是否定义了参考文献的版本和时效性需求？[Coverage, Gap]"

**漫画视觉一致性** (`visual-consistency.md`)：
- "角色设计的关键属性是否在所有出场话中有一致性需求？[Consistency]"
- "'画面冲击力'是否用具体的构图原则或视觉效果量化？[Clarity]"
- "换页节奏和翻页阅读速度是否有明确的需求定义？[Completeness, Gap]"
- "是否定义了对话框位置和阅读顺序的需求？[Coverage, Spec §分镜]"

**视频节奏** (`pacing-rhythm.md`)：
- "场次间的过渡风格是否有可验证的一致性需求？[Consistency]"
- "'紧张节奏'是否用具体的镜头时长和切换频率量化？[Clarity]"
- "对话和画面的节奏配合是否有明确的需求定义？[Completeness, Gap]"
