```text
$ARGUMENTS
```

**必须**在继续之前考虑用户输入（若不为空）。

## Pre-Execution Checks

1. 确认当前目录为 SpecForge 项目：检查 `.specforge/` 目录是否存在
2. 执行 `specforge show --paths-only` 获取当前活动 feature 路径：
   - 提取 `FEATURE_DIR`、`SPEC_FILE`、`IMPL_PLAN`、`TASKS_FILE`
   - 若任一为空，ERROR：无法确定 feature 上下文
3. 确认 `FEATURE_DIR/tasks.md` 存在，若不存在 ERROR：任务文件缺失，请先执行 `/specforge.tasks`
4. 执行 `specforge show --artifact tasks` 加载完整任务清单
5. 确认 plan.md 中的内容类型和输出目录约定
   - 执行 `specforge show --artifact plan` 加载创作上下文
   - 提取 `content_type` 字段确定输出目录结构

## Outline

目标：按阶段顺序执行 tasks.md 中的所有任务，将创作成果写入 `dist/{content_type}/` 目录，发现上游问题时回溯修复。

### 第 1 步：检查清单状态

若 `FEATURE_DIR/checklists/` 目录存在：

1. 扫描所有检查清单文件
2. 统计每个清单：
   - 总数：匹配 `- [ ]` 或 `- [X]` 或 `- [x]` 的行
   - 已完成：匹配 `- [X]` 或 `- [x]` 的行
   - 未完成：匹配 `- [ ]` 的行
3. 创建状态表：

```text
| 检查清单 | 总数 | 已完成 | 未完成 | 状态 |
|----------|------|--------|--------|------|
| content-quality.md | 12 | 12     | 0      | ✓ PASS |
| structure.md       | 8  | 5      | 3      | ✗ FAIL |
```

4. 计算总体状态：
   - PASS：所有清单 0 未完成项
   - FAIL：一个或多个清单有未完成项

5. **若任一清单未完成**：
   - 显示未完成项数量的状态表
   - **停止**并询问：「部分检查清单未完成。是否仍要继续实施？（yes/no）」
   - 等待用户回复后再继续
   - 用户说 "no"/"wait"/"stop"：停止执行
   - 用户说 "yes"/"proceed"/"continue"：继续第 2 步

6. **若所有清单已通过**：显示通过状态表，自动进入第 2 步

### 第 2 步：加载并分析实施上下文

读取设计制品以理解完整实施计划：

- **必须**：`FEATURE_DIR/tasks.md` — 完整任务清单和执行顺序
- **必须**：`FEATURE_DIR/plan.md` — 创作上下文、内容结构、阶段规划
- **若存在**：`FEATURE_DIR/data-model.md` — 核心要素和关系
- **若存在**：`FEATURE_DIR/contracts/` — 接口规范和模板契约
- **若存在**：`FEATURE_DIR/research.md` — 调研决策和约束
- **若存在**：`.specforge/constitution.md` — 宪法约束和治理规则
- **若存在**：`FEATURE_DIR/quickstart.md` — 快速上手指南和验证场景

### 第 3 步：验证输出目录结构

根据 plan.md 中的内容类型，确认或创建 `dist/` 输出目录：

| 内容类型 | 输出目录 | 文件命名示例 |
|----------|----------|-------------|
| 通用 | `dist/default/` | `output.md` |
| 小说 | `dist/novel/` | `第N章-标题.md` |
| 文章 | `dist/article/` | `标题.md` |
| 漫画 | `dist/comic/` | `第N话-脚本.md`、`角色参考.md` |
| 视频 | `dist/video/` | `第N集-分镜头脚本.md`、`台词本.md` |

若目录不存在，按计划中的约定创建。

### 第 4 步：解析 tasks.md 结构

从 tasks.md 提取：

- **任务阶段**：Phase 1 准备、Phase 2 基础、Phase 3+ 创作场景、Phase N 打磨
- **任务依赖**：顺序 vs 并行执行规则
- **任务详情**：ID、描述、文件路径、[P] 并行标记、[Scene] 标签
- **执行流程**：顺序和依赖要求

### 第 5 步：按阶段执行实施

严格遵守阶段顺序和任务依赖：

#### 阶段执行规则

1. **阶段整体**：完成每个阶段的所有任务后才进入下一阶段
2. **依赖顺序**：按依赖关系顺序执行，关注 Phase 2（基础）是 Phase 3+（所有场景）的前提
3. **并行任务 [P]**：不同文件的并行任务可同时执行
4. **文件协调**：影响相同文件的任务必须顺序执行
5. **验证检查点**：每个阶段完成后验证产出

#### 各阶段执行要点

**Phase 1 — 准备**：
- 验证目录结构
- 确认工具和模板可用
- 准备参考资料

**Phase 2 — 基础**：
- 创建/更新核心设定文件
- 定义关键元素（人物/世界观/论点）
- 准备所有创作场景共享的前置内容
- **重要性**：Phase 2 是所有后续阶段的前提，必须完全完成

**Phase 3+ — 创作场景**（按 S1、S2、S3... 顺序）：
- 每个场景按 tasks.md 中的顺序执行任务
- 每个场景完成后执行独立验证
- 将场景产出写入 `dist/{content_type}/`

**Phase N — 打磨**：
- 全局一致性检查
- 跨场景修订
- 最终质量验收

### 第 6 步：进度跟踪与错误处理

- 每个任务完成后：报告进度，在 tasks.md 中将复选框标记为 `- [x]`
- **非并行任务失败**：停止执行，诊断错误，向用户报告
- **并行任务 [P] 失败**：继续执行成功的任务，报告失败的任务供单独处理
- 提供清晰的错误消息和上下文用于调试
- 若实施无法继续：建议下一步操作

### 第 7 步：上游问题回溯修复

若在实施过程中发现上游制品（spec.md、plan.md、data-model.md）存在问题：

1. **记录问题**：具体描述发现的不一致或缺失
2. **分类严重度**：
   - 阻塞性：阻止当前步骤的执行
   - 非阻塞性：可以绕过，但影响质量
3. **对阻塞性问题**：
   - 停止当前阶段执行
   - 向用户报告：「发现上游制品 [文件] 存在问题：[描述]。是否需要回溯修复？」
   - 用户确认后，回溯修改上游文件，然后从受影响的阶段重新开始执行
4. **对非阻塞性问题**：
   - 继续执行但在报告末尾记录待办项
   - 建议在下一次迭代中修复

### 第 8 步：完成验证

1. 验证所有必需任务已完成（tasks.md 中所有非可选任务标记为 [x]）
2. 检查产出文件是否符合规格中定义的成功标准
3. 验证 `dist/` 目录中的文件符合命名和结构约定
4. 确认实施遵循 plan.md 的创作上下文
5. 报告最终状态和已完成工作总结

## Output

- **主要产出**：`dist/{content_type}/` 目录中的创作成果文件
- **任务状态**：更新后的 `FEATURE_DIR/tasks.md`（已完成任务标记为 [x]）
- **格式**：文件格式和命名遵循 plan.md 中的约定

## Stage Checkpoints

- [ ] 检查清单状态已验证（全部 PASS 或用户明确批准继续）

- [ ] Phase 2 基础完成：所有共享前提内容已产出
- [ ] 每个创作场景阶段完成后通过独立验证
- [ ] Phase N 打磨完成：全局一致性检查通过
- [ ] 所有任务在 tasks.md 中已标记完成状态
- [ ] 上游问题已记录并分类（若存在）

## 质量门禁

- 是否严格按阶段顺序执行（无跨阶段跳跃）？
- Phase 2（基础）是否在 Phase 3+（场景）开始前完全完成？
- `dist/{content_type}/` 中的文件命名是否遵循 plan.md 的约定？
- 是否对每个场景阶段执行了独立验证？
- 上游问题是否有明确的回溯修复流程？
- 所有 CLI 调用是否使用了 `--json` 参数（如适用）？
- 本文件中是否**不包含** git、branch、commit、hook 相关引用？

**下一步**：执行 `/specforge.review` 对产物进行最终审查。

## 实施策略指南

### MVP 优先实施

1. 完成 Phase 1（准备）和 Phase 2（基础）
2. 完成 Phase 3（场景 S1/P1）形成最小可交付
3. 验证 S1 产物后决定是否继续 S2、S3
4. 在全部场景完成后运行 Phase N（打磨）

### 增量交付策略

- 每个场景阶段完成后即可产出可评估的内容片段
- 场景 S1 产物可独立提供给测试读者反馈
- 后续场景基于反馈进行微调

### 错误恢复策略

- 非阻塞性上游问题：记录待办项，继续执行但标记影响范围
- 阻塞性上游问题：停止执行，建议回溯修复路径
- 内容质量问题：记录改进项，可在打磨阶段集中处理

### 进度跟踪

每个任务完成后：
1. 在 tasks.md 中将 `- [ ]` 改为 `- [x]`
2. 保存 tasks.md（原子覆盖）
3. 向用户报告：`[T0XX] 已完成 — <任务描述>`

若在执行过程中遇到需要更新任务清单的情况（如：发现遗漏任务、顺序需要调整）：
1. 记录变更理由
2. 在 tasks.md 中追加变更说明
3. 继续执行而不中断整体流程

### 内容类型实施指南

**小说实施**：
- 逐章起草，保持人物行为的一致性
- 每章完成后对照人物设定文件核查
- 输出文件：`dist/novel/第N章-标题.md`
- 标注依赖前一章的情节元素

**文章实施**：
- 逐段撰写，确保论证逻辑链顺畅
- 每段标注引用来源
- 输出文件：`dist/article/标题.md`
- 在完成全部段落后进行整体逻辑走查

**漫画实施**：
- 逐话编写分镜脚本，包括画面描述和对白
- 同步维护角色参考文档
- 输出文件：`dist/comic/第N话-脚本.md` + `dist/comic/角色参考.md`
- 确保角色视觉描述跨话一致

**视频实施**：
- 逐集编写分镜头脚本，包括镜头描述、对白和时长
- 同步维护台词本
- 输出文件：`dist/video/第N集-分镜头脚本.md` + `dist/video/台词本.md`
- 确保场次过渡标注清晰
