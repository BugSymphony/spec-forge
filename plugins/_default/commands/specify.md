## User Input

```text
$ARGUMENTS
```

**必须**在继续之前考虑用户输入（若不为空）。

## Pre-Execution Checks

1. 确认当前目录为 SpecForge 项目：检查 `.specforge/` 目录是否存在
2. 执行 `specforge list --detail --json` 确认当前活动 feature 上下文
   - 解析 JSON 输出中的 `content_type` 字段，确定当前内容类型
   - 若 `content_type` 为空，默认使用 `_default` 通用类型
3. 若 `.specforge/` 不存在，ERROR：项目未初始化，请先执行 `specforge init` 初始化项目
4. 确认 `.specforge/templates/spec-template.md` 模板文件存在
   - 若模板缺失，ERROR：规格模板缺失，请检查项目初始化完整性
   - 模板解析遵循优先级：`.specforge/templates/overrides/` → 项目本地模板 → 插件模板 → 核心模板

## Outline

本命令从用户提供的自然语言描述中创建功能规格说明。流程如下：

### 第 1 步：解析用户输入

从 `$ARGUMENTS` 中提取关键信息：

- **创作领域**：内容类型（{content_type_cn}）、目标受众、创作方向
- **核心目标**：用户最想达成的创作目的
- **内容规模**：预期字数、章节数、篇幅范围等
- **核心要素**：世界观设定、人物关系、论证方向等关键元素
- **约束条件**：时间限制、风格要求、平台限制等

**若用户输入为空**：ERROR "未提供功能描述。请提供创作项目的目标描述，例如：'创作一部面向青年的科幻小说，注重科学准确性和角色成长'"

### 第 2 步：预览并创建 Feature

1. **预览 feature 名称和路径**：
   ```bash
   specforge new "$ARGUMENTS" --dry-run --json
   ```
   解析 JSON 输出，获取 `feature_name`、`feature_directory`、`feature_number` 等字段，向用户展示预览信息。

2. **正式创建 feature**：
   ```bash
   specforge new "$ARGUMENTS" --json
   ```
   解析 JSON 输出，设置以下路径变量：
   - `FEATURE_DIR`: 功能目录路径（如 `specs/004-科幻小说`）
   - `SPEC_FILE`: 规格文件路径（`FEATURE_DIR/spec.md`）
   
   若 `specforge new` 失败，ERROR：创建 feature 失败，检查项目初始化状态和描述输入。

3. **验证 feature 目录创建**：
   - 确认 `FEATURE_DIR` 目录已创建
   - 确认 `SPEC_FILE` 已生成（`specforge new` 自动复制模板到目标位置）
   - 执行 `specforge show --paths-only` 确认路径变量设置正确

### 第 3 步：加载规格模板

1. 读取 `.specforge/templates/spec-template.md` 了解所需的章节结构
2. 若模板不存在，使用默认结构：
   - 创作目标
   - 内容规模
   - 创作场景（含 Why This Priority / Independent Test / Given-When-Then，最少 2 个）
   - 核心要素
   - 成功标准
   - 假设与约束

### 第 4 步：填写规格内容

按照以下顺序逐一填写模板各章节：

#### 4.1 创作目标

- 用 1-2 段描述创作意图和方向
- 明确目标受众和预期效果
- 说明内容类型的独特性
- **关键问题**：这个项目的核心创作目的和受益读者是谁？

#### 4.2 内容规模

- 列出具体的规模指标（根据内容类型调整）：
  - 小说：总字数范围、章节数、每章字数范围
  - 文章：字数范围、段落数
  - 漫画：总页数、话数、每话页数范围
  - 视频：总集数、每集时长（秒）、总时长
- 标注为估算值，后续阶段可调整

#### 4.3 创作场景（最少 2 个）

每个场景包含以下结构：
- **标题**：概括场景核心内容
- **Why This Priority**：为什么这个创作点具有优先级
- **Independent Test**：如何独立验证此创作点已完成
- **Given-When-Then**：
  - Given：初始状态或前置条件
  - When：执行的动作或过程
  - Then：预期的结果或产出
- 若无法从用户描述中推导出至少 2 个创作场景，ERROR："无法确定创作场景——描述过于模糊，请提供更多关于创作方向和结构的信息"

#### 4.4 核心要素

- 列出构成内容骨架的关键元素（人物、世界观、论点、分镜等）
- 每个要素给出简短描述和关系说明
- 若涉及数据/实体，记录属性和生命周期状态

#### 4.5 成功标准

- 定义可衡量、技术无关的验收标准
- 每条标准满足：可度量（含具体指标）、面向受众（从读者/观众角度描述）、可独立验证
- 示例：
  - ✅ "读者能在开场 3 章内理解核心世界观设定"
  - ❌ "每日发布 1 章"（可度量但偏向实施细节）
  - ✅ "篇章间情节转折连贯，无不合理断裂"
  - ❌ "角色对话不少于 100 句"（纯数据指标，未体现读者价值）

#### 4.6 假设与约束

- 记录填充过程中的合理推断
- 明确已知的外部约束（平台、格式、工具等）
- 对于无法确定的关键决策，使用 `[待澄清: 具体问题]` 标记
- **限制**：最多 3 个 `[待澄清]` 标记，仅用于对项目范围或质量有重大影响的决策

### 第 5 步：生成规格文件

将填写好的内容写入 `SPEC_FILE`：
- 保持模板的章节顺序和标题层级
- 替换所有占位符为具体内容
- 移除不适用的可选章节（不要保留 "N/A"）
- 确保 Markdown 格式正确

### 第 6 步：规格质量验证

验证生成的规格是否符合质量标准：

#### 6.1 创建质量检查清单

在 `FEATURE_DIR/checklists/requirements.md` 生成检查清单：

```markdown
# 规格质量检查清单：[功能名称]

**目的**：在进入计划阶段前验证规格的完整性和质量
**创建日期**：[当前日期]
**功能**：[链接到 spec.md]

## 内容质量

- [ ] 无实施细节（语言、框架、API）
- [ ] 聚焦于读者价值和创作目标
- [ ] 面向非技术利益相关者可读
- [ ] 所有必填章节已完成

## 需求完整性

- [ ] 无 [待澄清] 标记残留
- [ ] 成功标准可度量
- [ ] 成功标准技术无关（无实施细节）
- [ ] 所有创作场景已定义（最少 2 个）
- [ ] 边缘场景已识别
- [ ] 范围边界清晰
- [ ] 假设与依赖已明确

## 功能就绪性

- [ ] 所有创作目标有明确验收标准
- [ ] 创作场景覆盖主要创作流程
- [ ] 功能满足成功标准中定义的可度量成果
- [ ] 无实施细节渗入规格

## 备注

- 未完成项需要在进入 `/specforge.clarify` 或 `/specforge.plan` 前修正
```

#### 6.2 执行验证检查

对照检查清单逐项审核规格：
- 记录通过和失败的项
- 引用相关规格章节说明具体问题

#### 6.3 处理验证结果

- **全部通过**：标记清单完成，进入第 7 步
- **有失败项（不含 [待澄清]）**：
  1. 列出失败项和具体问题
  2. 更新规格解决每个问题
  3. 重新验证直到全部通过（最多 3 轮）
  4. 若 3 轮后仍失败：在清单备注中记录残留问题，警告用户
- **存在 [待澄清] 标记**：
  1. 提取所有 `[待澄清: ...]` 标记
  2. 若超过 3 个，仅保留 3 个最关键的（按范围 > 质量 > 受众影响排序）
  3. 对每个待澄清项，向用户展示选项：

```markdown
## 问题 [N]：[主题]

**上下文**：[引用相关规格章节]

**需要明确**：[待澄清标记中的具体问题]

**建议答案**：

| 选项 | 答案 | 影响 |
|------|------|------|
| A    | [第一个建议] | [对该功能的影响] |
| B    | [第二个建议] | [对该功能的影响] |
| C    | [第三个建议] | [对该功能的影响] |
| 自定义 | 提供您自己的答案 | [说明如何提供自定义输入] |

**您的选择**：_[等待用户响应]_
```

4. 问题编号为 Q1、Q2、Q3（最多 3 个）
5. 同时呈现所有问题，等待用户一次性回复
6. 根据用户选择替换 `[待澄清]` 标记
7. 澄清完成后重新运行验证

#### 6.4 更新检查清单

每次验证迭代后更新检查清单文件的通过/失败状态。

### 第 7 步：报告完成

向用户输出以下信息：

- **功能目录**：`FEATURE_DIR`
- **规格文件**：`SPEC_FILE`
- **检查清单结果摘要**：通过/失败项数
- **下一步建议**：
  - 若全部通过：建议执行 `/specforge.clarify` 或 `/specforge.plan`
  - 若有残留问题：建议先修正再继续

## Output

- **制品**：`FEATURE_DIR/spec.md`
- **质量检查清单**：`FEATURE_DIR/checklists/requirements.md`
- **格式**：Markdown，遵循模板结构
- **路径示例**：`specs/004-科幻小说/spec.md`

## Stage Checkpoints

- [ ] 用户输入已解析，核心目标已提取
- [ ] Feature 目录和规格文件已创建
- [ ] 所有必填章节已填充具体内容（无模板占位符残留）
- [ ] 创作场景至少 2 个，每个含 Why This Priority / Independent Test / Given-When-Then
- [ ] 成功标准可度量且技术无关
- [ ] [待澄清] 标记不超过 3 个，或已全部解决
- [ ] 质量检查清单已生成并验证通过
- [ ] 范围边界明确，假设已记录

## 质量门禁

- 规格中是否仅描述"什么"和"为什么"，不含"怎么做"的实施细节？
- 创作场景的 Given-When-Then 是否具体到可独立验证？
- 成功标准是否从读者/受众角度定义？
- 用户是否能直接从规格理解创作项目的目标和边界？
- 所有 CLI 调用是否使用了 `--json` 参数（如适用）？
- 本文件中是否**不包含** git、branch、commit、hook 相关引用？

**下一步**：执行 `/specforge.clarify` 进行结构化歧义扫描，或执行 `/specforge.plan` 创建创作计划。

## 快速指引

- 聚焦于**什么**（创作目标）和**为什么**（创作动机与受众价值），避免如何实施的内容
- 面向内容创作者而非技术开发者
- 不在此命令中创建嵌入规格的检查清单——检查清单是单独命令 `/specforge.checklist` 的职责
- 必填章节每个功能必须完成；可选章节仅在相关时包含；不适用时整体移除（不要保留 "N/A"）
- 做出合理推断并记录假设；最多 3 个 `[待澄清]` 标记，仅用于影响重大的关键决策
- 优先级排序：创作目标 > 受众适配 > 质量风格 > 细节设定
- 成功标准必须可度量、技术无关、面向读者/受众、可独立验证

**合理默认值示例**（不要询问以下方面）：
- 内容存储：与项目指定的文件组织保持一致
- 质量目标：遵循内容类型的标准行业实践
- 修订处理：友好迭代流程
- 集成模式：使用项目适合的模式（纯文本、Markdown 等）

**成功标准的好的示例**：
- "读者能在开篇 3 章内完成主要人物的初步认知"
- "正文内容覆盖 5 个以上核心论点，每个论点有 2 个以上支撑论据"

**成功标准的差的示例**（实施导向）：
- "使用 Markdown 格式输出"（太技术化）
- "每章 3000 字"（纯数据指标，未关联读者体验）
- "对话占比 30%"（未关联叙事节奏效果）
