# 文章规格说明

## User Input

```text
$ARGUMENTS
```

根据用户输入创建文章规格说明文件 `specs/<NNN>-<name>/spec.md`，定义文章的核心论点、目标受众、内容规模和论证要点。本阶段仅回答 **WHAT**（要写什么）和 **WHY**（为什么这样写），不涉及 **HOW**（怎么写）——段落结构、论证顺序、引用细节留给 plan 阶段。

## Pre-Execution Checks

1. 确认当前目录为 SpecForge 项目（存在 `.specforge/` 目录）
2. 执行 `specforge list --detail --json` 确认当前活动 feature 和项目上下文
3. 读取 `.specforge/constitution.md` 获取宪法约束，确保规格说明中所有写作原则和论证标准可被落实
4. 读取 `.specforge/templates/spec-template.md` 获取规格模板结构

## Outline

### 第 1 步：解析用户输入

- 从 `$ARGUMENTS` 中提取关键概念，按以下维度分类：
  - **核心论点（Core Thesis）**：文章要论证的中心主张（1-3 句提炼）
    识别标记词："主张"、"我认为"、"核心观点是"、"论点是"
    若输入无明确论点：根据输入的主题方向推断，并标注为"推断论点——请审查确认"
  - **目标受众（Target Audience）**：写给谁看
    识别标记词："面向"、"读者是"、"写给"
    受众维度：知识水平（入门/中级/专家）、角色（决策者/从业者/学生/大众）、阅读场景（快速浏览/深度阅读/决策参考）
    若输入未提受众，默认推断为"对主题有一定了解的普通读者"
  - **内容规模（Content Scale）**：预期字数和段落数
    识别标记词："3000字"、"约 5 段"、"10 分钟阅读"
    若输入未提规模：根据文章类型推断默认值并标注为"建议规模——请审查确认"
  - **论证要点（Key Arguments）**：支撑核心论点的关键论据（识别至少 2 个）
    识别标记词："因为"、"例如"、"证据"、"数据显示"、"研究表明"
    若输入仅含概括性主题而无具体论据，标注"论证要点不足——请在后续 clarify 阶段补充"
  - **参考来源（References）**：已提及的参考文献、数据来源或案例
    识别标记词："根据"、"引用"、"参考文献"、"来源"
    若输入未提来源，标注为"待填充"
  - **约束条件（Constraints）**：明确的写作限制
    识别标记词："不能"、"禁止"、"必须包含"、"不得"、"应该避免"
- 若用户输入为空，ERROR：提示用户提供文章描述
  - 最小有效输入示例："论证远程办公降低企业创新能力的核心论点，面向 HR 管理者，约 3000 字"
  - 最小有效输入示例："科普文：为何火星不适合人类移民，面向大众读者，约 2000 字，引最新 NASA 研究"

### 第 2 步：创建 feature 目录

- 先执行 `specforge new "$DESC" --dry-run --json` 预览 feature 名称和路径
- 解析 JSON 输出获取 `feature_name`、`feature_number` 和路径信息
- 向用户展示预览结果：
  - 编号：NNN
  - 目录名：NNN-{feature-name}
  - 路径：specs/NNN-{feature-name}/
- 提示用户确认或使用 `--short-name` 指定自定义名称
- 确认后执行 `specforge new "$DESC" --json` 创建 feature 目录
- 若目录已存在：提示用户已有同名 feature，建议使用不同描述或 `specforge use <name>` 切换
- 确认 `specs/<NNN-<name>/spec.md` 文件已创建（空模板）

### 第 3 步：提炼核心论点

将用户输入提炼为 1-3 句核心论点陈述：

**论点提炼规则**：
- 论点必须是可论证的命题（含主张 + 理由方向）
- 论点不能是纯事实陈述（事实不需要论证）
- 论点不能是个人偏好表达（偏好无需论证）
- 论点应是可证伪的——理论上存在反面证据可推翻它

**质量检查**：
- 论点是否清晰到可被一个独立读者理解？
- 论点是否有论证空间（非自明之理）？
- 论点边界是否恰当（非过于宽泛或过于狭窄）？

**示例**：
- ✅ 合格："远程办公降低企业创新能力，因为自发性知识共享的减少抵消了专注时间的提升"
- ❌ 不合格："远程办公是一个值得讨论的话题"（无可论证命题）
- ❌ 不合格："远程办公对员工有利"（过于笼统，边界不清）

若用户输入的核心论点不符合以上标准，给出修改建议并询问用户确认。

### 第 4 步：定义目标受众

将受众定义细化到以下维度，写入 spec：

- **主要受众**：一句话描述（如"企业中高层 HR 管理者"）
- **知识水平**：该受众对主题的预期了解程度（入门 / 中级 / 专家）
- **阅读场景**：受众在什么场景下阅读（决策参考 / 知识获取 / 观点验证）
- **受众关注点**：该受众最关心的 3-5 个问题或痛点
- **受众偏见**：该受众可能已有的预设立场或反对意见
- **适配策略**：一句话说明文章如何适配该受众（如"大量使用企业案例和数据图表，避免学术术语"）

若用户未提供足够受众信息，基于文章主题合理推断，标记为"推断受众——请审查"。

### 第 5 步：定义论证要点（最少 2 个）

为每个论证要点定义完整的 GIVEN-WHEN-THEN 验证骨架。论证要点是支撑核心论点的关键论据分支，每个要点应独立可论证。

**第 1 个论证要点**（优先级 P1——最核心的论据）：

- **名称**：简短摘要（如"自发性知识共享的衰退"）
- **描述**：该论证要点的完整说明（3-5 句），解释该要点如何支撑核心论点
- **Why This Priority**：为何该论证要点是最高优先级？
  - 说明该要点对核心论点的支撑力——核心论点的成立多大程度依赖于此要点
  - 说明该要点面对的最强反驳是什么，为什么仍能成立
- **Independent Test**：如何独立验证该论证要点是否成立？
  - 例如："可通过对比至少两个不同行业的远程办公企业创新指标来验证"
  - 例如："可通过引述至少 3 篇同行评议研究来验证"
- **Acceptance Scenarios**（使用 Given-When-Then 格式）：
  1. **Given** 文章引用了远程办公对自发互动的实证研究（如咖啡机对话效应），**When** 读者阅读该论证要点，**Then** 读者理解为何自发互动的减少与创新能力下降之间存在因果关系
  2. **Given** 文章给出了计划性沟通无法替代自发性互动的具体原因，**When** 读者评估该论据，**Then** 读者认可"工具可以计划交流但无法还原偶然碰撞"这一推理

**第 2 个论证要点**（优先级 P2）：

- 结构同第 1 个，但面向另一个独立的角度支撑核心论点
- 两个论证要点必须来自不同的论证角度（如第 1 个从实证数据角度，第 2 个从理论推理角度）
- 禁止两个论证要点互为依赖——每个须独立支撑论点

**第 N 个论证要点（可选，P3+）**：
- 建议不超过 5 个论证要点，保持文章焦点
- 若用户输入中能提取更多论据，按以下优先级排序：
  1. 直接支撑核心论点的论据（最高优先级）
  2. 回击反驳的论据（中等优先级）
  3. 补充背景的论据（最低优先级）

### 第 6 步：定义内容规模

将内容规模具体化为可度量的指标：

- **字数范围**：如"3000-4000 字"（含上下浮动 20% 的区间）
- **段落数**：主体段落数（不含引言和结论），如"6-8 个主体段落"
- **段落结构**：典型段落长度建议（如"每段 300-500 字"）
- **引用数量**：最小引用要求（如"至少 5 个独立来源"）
- **阅读时长**：估算目标阅读时长（如"约 15-20 分钟"）

若用户未指定规模，根据文章类型提供默认建议：
- 短篇评论：800-2000 字，3-5 个主体段落
- 深度分析：2000-5000 字，5-8 个主体段落
- 长篇研究：5000-10000 字，8-15 个主体段落

### 第 7 步：定义参考来源

列出已知和待确认的参考来源：

- **已确认来源**：用户输入中明确提及的参考文献、数据出处、案例
  - 每项记录：来源名称、作者/机构、类型（学术论文/报告/新闻/书籍/访谈）
- **待确认来源**：论证要点中需要但尚未明确的引用
  - 标注为 `[NEEDS CLARIFICATION: 需要何种来源支撑哪个论证要点]`
- **来源质量标准**（根据文章类型）：
  - 学术文章：优先同行评议期刊，禁止维基百科
  - 行业分析：优先一手数据和权威机构报告
  - 大众科普：优先知名科普机构和学者公开资料

### 第 8 步：定义成功标准

定义文章的质量验收标准，使用 SC-### 编号：

- **SC-001 论点清晰度**：读者在阅读引言后能用自己的话复述核心论点
  - 验证方式：给 3 名测试读者看引言部分，至少 2 人正确复述论点
- **SC-002 论证说服力**：每个论证要点满足"主张→证据→推理→结论"的完整链条
  - 验证方式：用论证逻辑链图逐一检查每个要点
- **SC-003 读者适配度**：目标读者平均理解评分 ≥ 4/5
  - 验证方式：目标受众代表阅读后打分
- **SC-004 引用可追溯性**：所有引用来源可被追溯到原始出处
  - 验证方式：逐一检查每条引用的原始链接或文献信息
- **SC-005 内容规模达标**：文章字数在指定范围内（±20%）
  - 验证方式：终稿字数统计

### 第 9 步：写入规格文件

- 读取 `.specforge/templates/spec-template.md` 获取结构
- 将第 3-8 步生成的内容填充模板，写入 `specs/<NNN>-<name>/spec.md`
- 填写元数据：Feature 名称、创建日期、状态（Draft）、用户输入原文
- **关键自检——确保没有 HOW 类内容渗入**：
  - ❌ 禁止：段落顺序安排（如"第一段先写X，第二段再写Y"）
  - ❌ 禁止：论证结构设计（如"采用递进式论证"）
  - ❌ 禁止：具体引用位置分配（如"第三段引用 A 研究"）
  - ❌ 禁止：写作风格指令（如"开头用设问吸引读者"）
  - ✅ 允许：论证要点的内容定义（"要论证什么" 而非 "怎么论证"）
  - ✅ 允许：规模约束（"含 5 个论证要点" 而非 "5 个要点的排列顺序"）
- 确认所有占位符已替换，无 `[TODO]`、`[NEEDS CLARIFICATION]` 之外的占位符

### 第 10 步：质量自检

执行以下自检清单：

1. **宪法一致性**：逐条对照宪法写作原则
   - 论点清晰性：核心论点是否可被独立理解？
   - 论证严谨性：是否每个论证要点都定义了验证方法？
   - 读者导向：是否定义了目标受众和适配策略？

2. **WHAT/WHY 边界**：全文是否无 HOW 类内容？
   - 遍历全文，搜索以下关键词：首先/然后/接着/最后/第一步/结构/开头/结尾
   - 若出现以上关键词且用于描述写作顺序，必须移除或改写为论证要点的内容描述

3. **论证要点完整性**：
   - 最少 2 个论证要点 ✓
   - 每个含 Why This Priority ✓
   - 每个含 Independent Test ✓
   - 每个含至少 1 个 Given-When-Then ✓

4. **规模可度量性**：字数范围、段落数、引用数量是否明确？

## Output

- **制品**：`specs/<NNN>-<name>/spec.md`
- **格式**：Markdown
- **位置**：当前活动 feature 目录下

## Stage Checkpoints

- [ ] 核心论点可被独立读者理解（1-3 句，含主张和理由方向）
- [ ] 目标受众定义了知识水平、阅读场景和适配策略
- [ ] 至少 2 个论证要点，每个含 Why This Priority / Independent Test / Given-When-Then
- [ ] 内容规模可度量（字数范围、段落数、引用数量）
- [ ] 参考来源已记录（已确认 + 待确认）
- [ ] 成功标准含至少 4 条 SC 编号条目
- [ ] 全文无 HOW 类内容（无段落顺序、论证结构设计、写作风格指令）
- [ ] 宪法一致性已自检通过

## 质量门禁

- 是否每个论证要点都有独立于其他要点的验证路径？
- 是否所有 Given-When-Then 场景可被独立测试？
- 是否有足够信息让 plan 阶段直接开始设计论证链而无须回头问"这是什么意思"？
- 是否所有 "待确认" / "推断" 标记都有明确路径传递到 clarify 阶段？

**下一步**：执行 `/specforge.clarify` 澄清模糊定义，或执行 `/specforge.plan` 生成实施计划
