# 文章审查

## User Input

```text
$ARGUMENTS
```

对 `dist/article/<标题>.md` 中的文章成品进行全面质量审查，聚焦逻辑一致性、论证质量、可读性和引用准确性。产出审查报告，给出修改建议或放行决定。

## Pre-Execution Checks

1. 确认当前目录为 SpecForge 项目（存在 `.specforge/` 目录）
2. 执行 `specforge list --detail --json` 确认当前活动 feature
3. 检查 `dist/article/` 目录是否存在成品文件
   - 若无成品文件：ERROR 提示先执行 `/specforge.implement`
4. 读取以下参考文件：
   - `specs/<NNN>-<name>/spec.md` — 原始规格（核心论点、论证要点、成功标准）
   - `specs/<NNN>-<name>/plan.md` — 实施计划（论证链设计、宪法合规检查）
   - `build/argument-chain.md` — 论证逻辑链
   - `build/citation-plan.md` — 引用清单（用于核对引用准确性）
   - `build/paragraph-outline.md` — 段落大纲（用于核对段落执行度）
   - `.specforge/constitution.md` — 宪法原则（用于宪法合规审查）

## Outline

### 第 1 步：结构完整性审查

检查文章的基本结构是否完整，是否对齐 plan 阶段的段落大纲。

**审查项**：
1. **段落覆盖**：成品中的段落是否覆盖了段落大纲中定义的所有段落？
   - 对比 paragraph-outline.md 中的段落列表和成品的实际段落
   - 缺失段落：标记为 `[MISSING]`，说明未覆盖的内容要素
   - 新增段落：标记为 `[EXTRA]`，说明新增段落是否合理（合理的新增接受，无理由的跑题标记为需删除）
2. **内容要素覆盖**：每个段落是否包含段落大纲中定义的内容要素？
   - 逐段检查 paragraph-outline.md 中的"内容要素"清单是否在成品中体现
   - 要素缺失：标记为 `[ELEMENT_MISSING]`
3. **论证要点覆盖**：spec 中定义的每个论证要点是否在成品中有充分展开？
   - 每个论证要点在成品中是否至少被 1 个段落充分论证
   - 论证要点覆盖度 = 已充分展开的论证要点数 / spec 中的论证要点总数
   - 覆盖率 < 100% 标记为 `[INCOMPLETE]`
4. **引用覆盖**：citation-plan.md 中的"已获取"引用是否在成品中实际使用？
   - 未使用引用：标记为 `[UNUSED_CITATION]`，说明是否需要使用或移除
   - 成品中出现了 citation-plan.md 未列的新引用：标记为 `[EXTRANEOUS_CITATION]`，评估其必要性

**产出**：结构审查矩阵表（通过 / 部分通过 / 未通过，附具体证据）。

### 第 2 步：逻辑一致性审查

审查文章的内在逻辑——是否存在自相矛盾、推理跳跃或逻辑谬误。

**审查维度**：

1. **核心论点一致性**：
   - 提取引言段的论点陈述和结论段的论点重述
   - 比较两者是否一致（允许表述方式不同，禁止立场变化）
   - 不一致：标记为 `[THESIS_DRIFT]` —— 引言立论 A，结论总结 B

2. **论证链完整性**：
   - 对照 build/argument-chain.md 中的论证逻辑链
   - 在成品中追踪论证链的每个节点是否有对应段落展开
   - 断裂：标记为 `[CHAIN_BREAK]` —— 节点 N 到 N+1 之间缺少段落桥接
   - 偏移：标记为 `[CHAIN_DRIFT]` —— 节点对应段落存在但论证方向偏离了原设计

3. **前后矛盾检测**：
   - 扫描全文中可能相互矛盾的断言
   - 重点关注：不同论证要点之间的立场冲突、同一概念在不同段落的定义不一致
   - 检测方法：
     - 提取所有明确断言句（"X 是 Y"、"A 导致 B"、"P 应 Q"）
     - 比较任意两个断言是否存在逻辑冲突
     - 若断言 A = "远程办公提升个人效率"，断言 B = "远程办公降低整体产出"，检查是否有中间论证调和二者
   - 矛盾未调和：标记为 `[CONTRADICTION]`
   - 矛盾已调和但调和不够充分：标记为 `[WEAK_RESOLUTION]`

4. **逻辑谬误扫描**：
   扫描以下常见逻辑谬误：
   - **以偏概全**：从个别案例推出普遍结论（"某公司远程办公后创新下降 → 远程办公降低创新"）
   - **因果倒置**：将结果当作原因（"企业创新低 → 所以远程办公多"——可能是创新低的企业更倾向远程办公）
   - **偷换概念**：论证过程中关键概念的内涵发生变化（如将"创新能力"悄然替换为"专利申请数"）
   - **诉诸权威**：仅以权威身份作为论据（"因为诺贝尔奖得主这样说"而无实际推理）
   - **假两难**：将问题简化为非此即彼（"要么全员远程，要么全员坐班"——忽略混合模式）
   - **滑坡谬误**：无依据地推断极端后果（"远程办公 → 创新下降 → 企业倒闭 → 经济危机"）
   - **虚假因果**：将相关性当作因果性（"A 与 B 同时发生 → A 导致 B"）
   - 每发现一处，标记为 `[FALLACY:<类型>]`，附受影响文本和修正建议

**产出**：逻辑审查报告，按维度分类，每项含严重度（CRITICAL / MAJOR / MINOR）。

### 第 3 步：论证质量审查

评估每个论证要点的论证深度和说服力，不限于有无结构而在于结构质量。

**审查维度**：

1. **论证深度评分**（每个论证要点 1-5 分）：
   - 1 分：仅有主张，无证据或推理（"远程办公降低创新"——仅断言）
   - 2 分：有主张 + 1 条证据，无推理连接（引了一项研究但未解释其意义）
   - 3 分：主张 + 证据 + 简单推理（解释了证据如何支持主张，但未深入）
   - 4 分：主张 + 多源证据 + 递进推理 + 考虑了反驳（"有研究表明 X，但也有人质疑 Y，本文认为 Z 是因为..."）
   - 5 分：除 4 分外，还含理论框架解释、边界条件讨论、读者可自行验证的方法论

2. **证据充分性检查**（每个论证要点）：
   - 证据数量 ≥ 在 citation-plan.md 中分配的引用数下限？
   - 多样性：证据是否来自不同类型（数据+案例+权威观点，而非全同一种）？
   - 时效性：非历史性引用是否来自近 5 年？代表性：案例是否典型而非特例？
   - 不足处标记为 `[EVIDENCE_INSUFFICIENT:<类型>]`

3. **推理质量检查**（每个论证要点）：
   - 是否存在"因为 A 所以 B"但缺中间推理链条的跳跃？
   - 推理过程是否可被一个理性读者跟随并认可？
   - 推理中是否隐含了未经论证的前提假设？
   - 问题标记为 `[REASONING_GAP]` 或 `[HIDDEN_ASSUMPTION]`

4. **反驳处理检查**：
   - 对于 spec 中目标受众的"偏见/预设立场"，成品是否有回应段落？
   - 回应的反驳是否是有力版本（最强反驳）而非稻草人版（弱化版）？
   - 对反驳的回应是否充分（承认合理部分 + 给出论证边际 + 指出反驳不成立的边界条件）？
   - 不足处标记为 `[STRAWMAN]`（攻击弱化反驳）或 `[UNANSWERED_CHALLENGE]`（完全未回应）

**产出**：论证质量评分卡（每个论证要点的深度评分 + 证据/推理/反驳三个维度的诊断）。

### 第 4 步：可读性审查

评估文章的语言质量和读者体验。

**审查维度**：

1. **语言适配度**：
   - 逐段检查语言难度是否匹配 spec 定义的目标受众知识水平
   - 专家受众：是否无冗余基础概念解释？
   - 大众受众：所有专业术语是否在首次出现时给出定义或类比解释？
   - 未定义术语：标记为 `[UNDEFINED_TERM]`
   - 过度简化（面向专家的文章过多基础解释）：标记为 `[OVERSIMPLIFIED]`

2. **段落节奏评估**：统计每段字数和段落长度分布
   - 过长段落（> 600 字需分拆）/ 过短段落（< 100 字，论证可能不充分）/ 相邻段落长度差异过大
   - 问题标记为 `[PACING]`

3. **句式复杂度**：
   - 抽样 10 个句子，计算平均句长（字数）
   - 中文可读性参考：平均句长 > 40 字可能造成阅读困难
   - 统计嵌套从句密度：是否有句子含 3+ 层嵌套？
   - 统计被动语态使用率：过多被动语态降低力度（议论文应主动语态为主）
   - 问题标记为 `[SENTENCE_COMPLEXITY]`

4. **过渡与衔接**：
   - 朗读每个段落的最后一句和下一段的第一句
   - 过渡是否自然？还是段落间出现话题断裂？
   - 过渡词/衔接词使用是否恰当且多样化（"此外"、"然而"、"更重要的是"、"与此相对"）？
   - 若有 3+ 段连续以相同过渡词开头，标记为 `[REPETITIVE_TRANSITION]`

5. **信息密度评估**：文章是否出现"注水段"（大量文字缺乏实质信息）？
   - 评估方法：用 1 句话概括每段，若概括后无信息丢失则该段可能注水；去除修饰语后核心论证仍完整则为合格
   - 注水段标记为 `[LOW_DENSITY]`

**产出**：可读性审查报告（语言适配、节奏、句法、衔接、信息密度五个维度的诊断和示例）。

### 第 5 步：引用准确性抽查

对文章中的引用进行抽样验证，确保引用准确且可追溯。

**抽样策略**：
- 若全文引用数 ≤ 10：全量检查
- 若全文引用数 11-30：抽查 50%（最少 10 条）
- 若全文引用数 > 30：抽查 30%（最少 15 条）
- 优先抽查：核心论证要点中的引用、数据类引用（最易出错）、看似"太精确"的数字

**每项引用检查**：
1. 来源是否存在？（URL 可访问 / 文献可检索）
2. 信息是否被准确转述？（对比原文 vs 文章摘录）
3. 数据是否准确？（数字、百分比、年份是否与原文一致）
4. 引用是否断章取义？（上下文是否与原文一致）

**错误分级**：
- CRITICAL：数据完全错误或来源不存在
- MAJOR：数据有偏差但不影响论证（如"35%"实为"34.5%"）
- MINOR：信息正确但格式不规范（如缺少年份）

**产出**：引用抽查表，含检查项、错误分级、修正建议。

### 第 6 步：宪法合规终审

对成品进行最终宪法合规检查，与 plan 阶段的宪法检查形成闭环。

**逐条原则检查**：
1. **论点清晰性**：读引言段后，是否能在 10 秒内找到核心论点句？
2. **论证严谨性**：是否每个论证要点都有可追溯的引用支撑？
3. **读者导向**：以目标受众身份阅读时经历是否顺畅？术语是否定义？
4. **结构均衡性**：引言 / 主体 / 结论的比例是否合理？
5. **语言风格**：全篇语言风格是否与宪法定义一致且统一？

**论证标准逐条评估**：
- QS-005 论点鲜明性：核心论点是否前后一致？
- QS-006 论证完整性：每个要点的主张→证据→推理→结论链条是否实际存在？
- QS-007 逻辑一致性：是否无矛盾？
- QS-008 读者适配性：是否匹配目标受众？

**合规判定**：
- 全部通过 → 标记为 `[CONSTITUTION_PASS]`
- 部分未通过 → 标记为 `[CONSTITUTION_PARTIAL]`，列出具体违规项和严重度
- 严重违规 → 标记为 `[CONSTITUTION_FAIL]`，建议回退 implement 修改

### 第 7 步：成功标准对照

对照 spec 中的成功标准 SC 条目进行逐条实际验证：

- **SC-001 论点清晰度**：独立读者（审查者自身脱离写作者身份）是否能复述核心论点？
- **SC-002 论证说服力**：逐条检查论证链条，是否每个要点都满足完整结构？
- **SC-003 读者适配度**：是否可合理预期目标受众的平均理解 ≥ 4/5？
- **SC-004 引用可追溯性**：抽查结果——追溯成功率是多少？
- **SC-005 内容规模达标**：实际字数与目标范围比较

**判定**：
- 所有 SC 通过 → 文章可放行
- 部分 SC 未通过 → 标注修复优先级和建议方案
- 核心 SC（SC-001 + SC-002）未通过 → 建议回退，不可放行

### 第 8 步：生成审查报告

汇总第 1-7 步的所有发现，生成结构化审查报告。

**审查报告结构**：
```markdown
# 文章审查报告：[文章标题]

**审查日期**：[DATE]
**审查范围**：`dist/article/<标题>.md`
**参考文档**：spec.md / plan.md / argument-chain.md / citation-plan.md / paragraph-outline.md
**审查结论**：[APPROVED / APPROVED WITH SUGGESTIONS / REVISION REQUIRED]

## 总体评估
- 逻辑一致性：[评分]
- 论证质量：[评分]
- 可读性：[评分]
- 引用准确性：[评分]
- 宪法合规：[PASS / PARTIAL / FAIL]
- 成功标准达成：[N]/[M]

## 严重问题（CRITICAL）
[每个问题含：类别 / 位置（段落号）/ 描述 / 修复建议]

## 主要问题（MAJOR）
[同上格式]

## 轻微问题（MINOR）
[同上格式]

## 逐项诊断
### 论证要点 1：[名称] — 评分 [X]/5
[诊断细节]

### 论证要点 2：[名称] — 评分 [X]/5
[诊断细节]

...

## 引用抽查结果
[抽查表]

## 修改优先级建议
1. [最高优先级修改项]
2. [次优先级修改项]
...

## 放行建议
[若 APPROVED WITH SUGGESTIONS：哪些建议必须在发布前完成？哪些可后续迭代？]
```

**审查报告位置**：写入 `specs/<NNN>-<name>/review.md`

## Output

- **制品**：`specs/<NNN>-<name>/review.md`
- **格式**：Markdown（结构化审查报告）
- **位置**：当前活动 feature 目录下

## Stage Checkpoints

- [ ] 结构完整性已检查（段落覆盖、内容要素、论证要点覆盖、引用覆盖）
- [ ] 逻辑一致性已检查（论点一致性、论证链完整性、前后矛盾检测、逻辑谬误扫描）
- [ ] 论证质量已评估（深度评分、证据充分性、推理质量、反驳处理）
- [ ] 可读性已审查（语言适配、段落节奏、句式复杂度、过渡衔接、信息密度）
- [ ] 引用准确性抽查已完成（按抽样比例）
- [ ] 宪法合规终审已完成（对照宪法所有原则和论证标准）
- [ ] 成功标准逐条对照已完成
- [ ] 审查报告含总体结论和修改优先级

## 质量门禁

- 审查报告是否提供了可操作的修改建议（非仅描述问题）？
- 每个问题是否标注了严重度（CRITICAL / MAJOR / MINOR）？
- 每个问题是否定位到具体段落或句子（非泛泛而谈"整体需要改进"）？
- 放行建议是否基于成功标准的客观达成情况（非主观喜好）？
- 审查结论是否为 APPROVED / APPROVED WITH SUGGESTIONS / REVISION REQUIRED 三者之一？

**完成**：审查报告已输出，SDD 文章创作流程闭环完成。若需修改，可重新执行 `/specforge.implement` 修复后再次审查。
